1. System overview

Purpose: Manage 10 showroom parking spots. Cars come only from matched Data Uploader records. Staff use the Controller; the Dashboard is read-only for TV display.

Pages & roles

  • showroom-uploader.html — Upload Sales Raw Data + Leads in Progress. Match rule: Transaction Number = CRM Lead ID. Builds the car pool.
  • showroom-controller.html — Assign cars to parking 1–10, set Istimara/delivery, confirm deliveries. Password required.
  • showroom-dashboard.html — Parking grid only, car images by product, refreshes every 10 seconds. No password.
  • showroom-record.html — History log of parking events.

Parking layout

  • Spots 1–7 — Normal showroom parking.
  • Spots 8, 9, 10 — Delayed zone (highlighted purple). Cars that missed delivery time move here.

2. Data setup flow (before parking)

START → Data Uploader opens
ACTION: Upload Excel file 1 — Sales Raw Data
ACTION: Upload Excel file 2 — Leads in Progress (sheet: raw data all status)
ACTION: System matches rows where Transaction Number = CRM Lead ID
DECISION: Any matches?
→ NO: Pool empty — Controller shows “upload data first”
→ YES: Matched cars become parking pool (available for assignment)
END (ready for Controller)

3. Assign car to parking (Controller)

START → Staff clicks empty parking spot (1–10)
ACTION: Open parking modal
ACTION: Type VIN in search box OR pick from dropdown (matched pool only)
DECISION: Istimara issued?

Path A — No Istimara

ACTION: Save parking
STATE: Spot = Occupied
ACTION: Record event: assigned
ACTION: Dashboard shows car image + VIN
END (car stays until staff clears spot or re-assigns)

Path B — Istimara issued

ACTION: Check “Istimara issued”
ACTION: Set delivery date & time
ACTION: Select next car (replacement) — VIN search or dropdown
ACTION: Set next car arrival time (must be within 30 min before delivery, and before delivery time)
ACTION: Save parking
STATE: Spot = Delivery Booked (or Awaiting Replacement if replacement not yet arrived)
ACTION: Record event: assigned
END (wait until delivery time)

4. Delivery time passes (automatic)

TRIGGER: Current time ≥ delivery appointment time
ACTION: System does NOT auto-deliver
ACTION: Mark car: deliveryDelayed = true, awaitingDeliveryConfirm = true
ACTION: Store originSlot (which parking spot the car came from)
ACTION: Move car to first free slot in 8, 9, or 10
ACTION: Clear original parking spot (now empty for next car later)
STATE: Delayed zone = Confirm Delivery (pulsing red on Controller)
ACTION: Record event: delayed
ACTION: Dashboard updates (10s poll or live WebSocket)
END (wait for staff confirmation)

If delayed zone 8–10 is full, car stays on current spot but still marked delayed + awaiting confirm.

5. Delivery confirmation (Controller — manual)

START → Staff taps parking spot with Confirm Delivery or Delayed status
ACTION: Open modal: “Has this customer collected the vehicle?”
DECISION: Customer collected car?

Path A — YES (Delivered)

ACTION: POST confirm-delivery { delivered: true }
ACTION: Record event: delivered
DECISION: Replacement car was assigned?
→ YES: Promote replacement VIN into originSlot (original parking number, e.g. 3)
→ NO: Origin slot stays empty
ACTION: Clear delayed zone slot (8/9/10)
STATE: New car in origin slot = Occupied (no Istimara until staff edits)
END

Path B — NO (Still delayed)

ACTION: POST confirm-delivery { delivered: false }
ACTION: Record event: not_delivered
STATE: Car remains in delayed zone = Delayed
ACTION: awaitingDeliveryConfirm = false (no longer pulsing)
END (staff can tap same spot again later when customer arrives → back to decision “collected?”)

6. Clear parking spot

START → Staff opens parking modal → Clear spot
ACTION: Record event: cleared
STATE: Spot = Empty
END

7. Parking status reference (for flowchart labels)

  • Empty — No car assigned
  • Occupied — Car present, no Istimara / no delivery scheduled
  • Delivery Booked — Istimara + delivery time set, waiting for appointment
  • Awaiting Replacement — Replacement car arrival is still in the future
  • Confirm Delivery — Delivery time passed; staff must answer yes/no
  • Delayed — Customer did not collect; car in zone 8–10

8. Record events (for Records page / audit trail)

  • assigned — Car saved to a spot
  • delayed — Delivery time passed, moved to delayed zone
  • delivered — Staff confirmed customer collected
  • not_delivered — Staff confirmed customer did not collect
  • cleared — Spot manually cleared

9. Dashboard behavior (read-only)

  • Shows parking grid 1–10 only (no KPIs, no flight table)
  • Car image loaded from /images/cars/{product}.png (with fallbacks)
  • Spots 8–10 visually marked as delayed zone
  • Refreshes every 10 seconds + live WebSocket when available
  • TV mode: showroom-dashboard.html?tv=1

10. Suggested flowchart swimlanes

  1. Data Uploader — Excel upload & matching
  2. Controller staff — Assign, Istimara, confirm delivery, clear
  3. System (automatic) — Timeout at delivery time, move to delayed zone, promote replacement on confirm
  4. Dashboard (display) — Reflect current parking state
  5. Customer — Arrives for delivery (external trigger for confirm yes/no)

11. Main flow (one-line for top of chart)

Upload & match data → Assign car to parking → [Istimara?] → [Yes: schedule delivery + next car] → Wait → [Time passed] → Move to delayed 8–10 → Ask “Delivered?” → [Yes: record + next car to origin slot] / [No: stay delayed, ask again later]

12. API endpoints (optional technical box)

  • GET /api/showroom-board — Full board + parking slots
  • PUT /api/showroom-board/parking/:slot — Assign / update spot
  • POST /api/showroom-board/parking/:slot/confirm-delivery — Body: { delivered: true|false }
  • DELETE /api/showroom-board/parking/:slot — Clear spot
  • POST /api/showroom-board/import-sales-raw — Upload sales file
  • POST /api/showroom-board/import-leads-in-progress — Upload leads file
